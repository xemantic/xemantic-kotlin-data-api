# CLAUDE.md

This file captures only what cannot be inferred from the codebase itself.

## Rules for editing this file

Both developers and AI agents are expected to add entries as they encounter surprises.

- **Add an entry** when you encounter something unexpected: a build quirk, a non-obvious constraint, a dependency gotcha, or any behavior that would surprise the next agent or developer.
- **Add an entry** when a developer flags an anti-pattern produced by AI — describe the anti-pattern and the preferred alternative.
- **Do not** add codebase overviews, directory listings, or anything discoverable by reading the source.
- Keep entries concise: one line per lesson, grouped under a heading if a theme emerges.

## Known gotchas

- Do **not** call `xemantic { applyAllConventions() }` in this multimodule build. `applyAllConventions()` includes `applyJarManifests()`, which runs `configureEach` over every `Jar` task across `allprojects` and eagerly calls `archiveBaseName.get()`. The Kotlin Multiplatform `allMetadataJar` has no `archiveBaseName`, so the call fails with "Cannot query the value of task ':…:allMetadataJar' property 'archiveBaseName' because it has no value available." Apply the conventions individually and omit `applyJarManifests()` (same workaround as the multimodule `xemantic/markanywhere` project).
- `applyJReleaserConventions()` also assumes a single-module build: it makes the root project's `jreleaserAnnounce` depend on a root `publishToMavenCentral`, a task the vanniktech plugin creates only in the project it is applied to — here the subprojects, not the root. The root build script therefore registers an aggregate task of that name. Without it the release workflow (`build publishToMavenCentral jreleaserAnnounce`) fails during task-graph resolution, before anything is built or published, with nothing in the CI log but "Task with name 'publishToMavenCentral' not found in root project". Release-only wiring like this is checkable locally: `./gradlew jreleaserAnnounce --dry-run --no-configuration-cache -Pversion=<v>`.
- The build logs "The com.github.ben-manes.versions plugin id is deprecated; apply io.github.ben-manes.versions instead." Do **not** just swap the id in `libs.versions.toml`: `applyReportOnlyStableDependencyUpdates()` hooks `pluginManager.withPlugin("com.github.ben-manes.versions")`, and applying the plugin under its new id registers only that id, so the hook stops firing and the `rejectVersionIf` stable-only filter is silently lost — `versionCatalogUpdate` would then rewrite the catalog with alpha/beta/rc versions. (The legacy id still works because `LegacyVersionsPlugin` applies `VersionsPlugin` by class and Gradle registers *both* ids.) The warning goes away only once the conventions plugin hooks both ids.
- The binary-compatibility-validator expects a per-module API dump at `<module>/api/<module>.api`. After adding/changing public API run `./gradlew apiDump`; otherwise `build` fails on `apiCheck`/`jvmApiCheck`.
- The convention plugin sets `progressiveMode = true`, which turns the K2 compiler's *old IR argument API* deprecations into hard errors. In IR generation use the new flat model: `function.parameters` filtered by `IrParameterKind.Regular` (not `valueParameters`/`dispatchReceiver`), set arguments via `call.arguments[irValueParameter] = expr`, and pass type arguments through the `irCall(symbol, returnType, typeArguments)` overload (not `putTypeArgument`).
- Since Kotlin 2.3, `CompilerPluginRegistrar` has an abstract `pluginId` that **must equal** the `CommandLineProcessor.pluginId` (both use `DATA_API_PLUGIN_ID`). `PluginCliParser` pairs a registrar with its command-line processor by matching these ids; a mismatch (or a missing override) fails compilation. Keep both — and the Gradle plugin's `getCompilerPluginId()` — pointing at the same string.
- When a FIR `FirDeclarationGenerationExtension` synthesizes declarations, Fir2Ir auto-generates the IR bodies for `var` properties (backing field + accessors) and for constructors created with `generateDelegatedNoArgConstructorCall = true`. Plain functions (the builder's `build`, the factory function, `copy`) and the generated `equals`/`hashCode`/`toString` need hand-written IR bodies in the `IrGenerationExtension`; Fir2Ir does **not** auto-fill data-class members for plugin-generated functions.
- `equals`/`hashCode`/`toString` bodies are delegated to the compiler's own `IrBasedDataClassMembersGenerator` (the `data` class codepath). Two non-obvious requirements: (1) you must implement `getHashCodeFunctionInfo(IrType)` yourself — the FIR backend's override is `shouldNotBeCalled()` because it resolves hashCode via FIR, so a pure-IR plugin resolves the type's member `hashCode` (falling back to `Any.hashCode`); (2) its constructor needs `context.symbolTable`, whose getter requires `@OptIn(ObsoleteDescriptorBasedAPI::class)`. Declare the three members as `status { isOverride = true }` member functions in FIR so the IR functions arrive bodiless. The FIR generator must **skip** any of the three the user already declares (match `equals` by its *full* signature — one value parameter typed `Any?`, since a typed `equals(other: Money)` overload does not override `Any.equals`; `hashCode`/`toString` by zero parameters) — otherwise you get a "Platform declaration clash" on the duplicate `toString`/etc.
- To exercise the in-repo compiler plugin from a KMP module (e.g. `xemantic-kotlin-data-api-test`) without going through `DataApiGradlePlugin`'s published-artifact path, add the compiler-plugin project to every per-compilation classpath: `configurations.matching { it.name.startsWith("kotlinCompilerPluginClasspath") }.configureEach { add(name, project(":xemantic-kotlin-data-api-compiler-plugin")) }`. The JVM-only `"kotlinCompilerPluginClasspath"(project(...))` form covers only one configuration; KMP creates one such configuration per target/compilation (JVM/JS/Wasm/Native all run the plugin on the host JVM, so the single JVM plugin jar resolves for every backend).
- The IDE/language-server analyzer does **not** run this compiler plugin, so code using the synthesized `Builder` DSL / factory function (e.g. `Person { … }`, `Company { … }`, `Page.Builder<String>()`) shows false "Unresolved reference" / "No value passed for parameter" diagnostics. Ignore them — verify against `./gradlew :xemantic-kotlin-data-api-test:jvmTest`, which compiles and passes.
- The IR builder DSL (`org.jetbrains.kotlin.ir.builders`) has **no `irThrow` and no `irNot`** in Kotlin 2.3. Build a `throw` with the `IrThrowImpl(startOffset, endOffset, context.irBuiltIns.nothingType, exception)` factory from `...ir.expressions.impl` (the public ctor takes an `IrElementConstructorIndicator` — call the same-named top-level factory instead), and negate a Boolean as `irEquals(expr, irFalse())`. The helpers `irEqualsNull`, `irIfThen`, `irConcat`, `irString` *do* exist. For built-in collection symbols prefer `context.irBuiltIns.{mutableListClass,collectionClass,stringClass}` over the deprecated `referenceClass(ClassId(...))!!`.
- Primary-constructor **default values** cannot be delegated to the constructor call in `build()`: omitting an argument is a compile-time structural property of the IR call, while the builder only learns at runtime which properties were assigned. So `build()` inlines a copy of each default expression, resolving properties into locals in declaration order and rewiring the copied expression's `IrGetValue`s from the constructor's `IrValueParameter`s to those locals — that is what lets a default refer to a preceding property.
- Constructor hiding uses `private`, not `internal`: the JVM backend emits an `internal` constructor as `ACC_PUBLIC`, because a constructor cannot be name-mangled the way an internal function is, so Java keeps calling it positionally. `build()` reaches the private constructor from the nested `Builder` through the synthetic accessor the backend generates for that pattern — no extra IR needed, on any backend. `DataApiReflectionTest` asserts `Modifier.isPrivate` on the *Java* constructors, since `KVisibility` only reflects the Kotlin metadata and would pass either way.
- `getCallableNamesForClass` / `getNestedClassifiersNames` can be called as early as **supertype resolution** — it takes only another plugin generating declarations for the same class to pull them there, since supertypes of generated nested classes are resolved by walking their declared member scopes. So nothing computing a *name* may touch a resolved type (`resolvedReturnType`, `resolvedBounds`), or the compilation dies with "Expected is FirResolvedTypeRef, but was FirUserTypeRefImpl" as soon as a second plugin is on the classpath. Hence `dataPropertyNames` (raw names + `hasDefaultValue`) separate from `dataProperties` (typed, used only from `generateProperties`), and the user-declared `equals` matched through the unresolved type reference.
- A plugin-generated class can be given members **only by the plugin that generated it** (`FirGeneratedMemberDeclarationsStorage.getExtensionsForClass` filters to the owner generator), and two plugins generating a nested class of the same name is an `IllegalStateException` from the compiler, not a diagnostic. Members can be generated into a *declared* companion by any number of plugins. This is why the DSL entry point is a **function named after the class** rather than a companion `invoke`: generating no companion at all is what makes `@Serializable` `@DataApi` classes work with no boilerplate. The one place a companion is still needed is the host of a *nested* class's factory, and the plugin never generates that one either — it requires the enclosing class to **declare** a `companion object`, and reports a violation otherwise. Generating it would silently add a public `Companion` to a class its author never annotated (part of that class's binary API from then on, and an unexplained entry in the `apiDump`), and would collide with *any* other companion-generating plugin, not only kotlinx.serialization — so the rule is uniform rather than special-cased on `@Serializable`. An enclosing `object` — including a companion object, which cannot have a companion of its own — hosts the factories of the classes nested in it directly.
- The factory function is generated at **top level** for a top-level class (`getTopLevelCallableIds()` + `generateFunctions(callableId, context = null)`, both behind `@OptIn(ExperimentalTopLevelDeclarationsGenerationApi::class)`), and into the **enclosing type** for a nested one — its companion, or the object itself, since an `object` cannot have a companion but hosts the factory directly. Enumerating the annotated classes for the top-level ids needs a `LookupPredicate` (`predicateBasedProvider.getSymbolsByPredicate`), which is a different type from the `DeclarationPredicate` used for `matches`; register both.
- On the JVM a generated top-level function lands in a synthetic `__GENERATED__CALLABLES__Kt` file facade, not in `<SourceFile>Kt`. Invisible from Kotlin; it is the name Java callers would have to use, so don't promise a stable JVM entry point for the DSL.
- In IR, which body a plugin-generated function needs is dispatched on **where it was generated into**, never on its name alone: a class may legally be called `copy` or `build`, and its factory — named after it — would otherwise be routed to the member generator of that name and crash on a `parentAsClass` it does not have. The builder is identified structurally (`name == Builder` *and* `origin.pluginKey == DataApiPluginKey`), the `@DataApi` class by declaring such a builder, and anything else generated by this plugin is a factory. The factory's *target* still has to come from its return type, not its parent — it has no parent class when top-level — which also gives the correct substituted type arguments for a generic class for free.
- The `Builder` mirrors the class's type parameters onto its own copies (a nested class cannot use the enclosing class's), and everything read off the constructor is substituted onto them — `substitutorByMap` in FIR, `IrTypeParameterRemapper` in IR (also passed to `deepCopyWithSymbols` so a copied default expression is re-typed). Bounds cannot be mirrored: bound providers run eagerly while the builder class is built, during supertype resolution, before any bound has a resolved type — so bounded type parameters are rejected, and the "does it declare a bound" test has to be phase-stable (`it !is FirImplicitNullableAnyTypeRef`, true both before and after resolution) or the generator and the checker disagree and you get neither generation nor a diagnostic.
- Requiredness is decided by `IrType.isMarkedNullable()`, not `isNullable()`: an unbounded `T` is nullable through its implicit `Any?` bound, so `isNullable()` would silently make every `T`-typed property optional. But *neither* is the whole answer for a property typed as a **bare type parameter**, which is declared non-null yet legitimately holds null once the caller instantiates it nullably (`Response<String?, …>`): such a property gets an `$isAssigned` flag like a defaulted one, is missing only when never assigned, and its value reaches the constructor through `irImplicitCast` rather than `requireNotNull`, which would reject the null the caller explicitly asked for. Where `requireNotNull` *is* used it is bounded by `T : Any`, which a bare type parameter does not satisfy — pass `type.makeNotNull()` as its type argument.
- Whether a default applies is decided by a private `<property>$isAssigned` flag, **never** by the property being null — the builder types every property as nullable, so null alone cannot distinguish "left unset" from "explicitly assigned null". The flag is declared in FIR (`visibility = Visibilities.Private`; the `$` keeps it out of reach of user property names, which cannot contain one) only for defaulted properties, and in IR its backing field gets an explicit `false` initializer while the property's Fir2Ir-generated setter body is replaced with `field = value; <property>$isAssigned = true`. Consequences to preserve: a defaulted property counts as missing only when *explicitly* assigned null while its constructor parameter is non-nullable, and `copy` re-assigns through those same setters, so it carries nulls over instead of re-defaulting them.

- Unsupported class shapes must be rejected by `DataApiCheckersExtension` **and** skipped by `DataApiBuilderGenerator` (both go through `dataApiViolation()`). Reporting alone is not enough: FIR generation runs during resolution, long before checkers, so a half-generated unsupported class produces resolution noise — or an IR crash — that buries the diagnostic. Keep `dataApiViolation()` on `rawStatus` only; it is called from `getNestedClassifiersNames`, far too early for `resolvedStatus`.
- `com.intellij.psi.PsiElement` is **relocated** in `kotlin-compiler-embeddable` (to `org.jetbrains.kotlin.com.intellij.psi`), so a diagnostic factory cannot be declared as `error1<PsiElement, …>()` the way the compiler's own containers do. Use a Kotlin PSI type instead (`error1<KtDeclaration, String>()`) — it is unrelocated, and the CLI reports through light-tree sources anyway. A plugin's `KtDiagnosticsContainer` also has to be handed to `registerDiagnosticContainers(…)` in the `FirExtensionRegistrar`, or its messages render as a bare factory id.
- Markdown files in this repo (`README.md`, `CLAUDE.md`, docs) have **no line-width limit** — editors soft-wrap them. Never hard-wrap a sentence to fit a column; break only on [semantic boundaries](https://sembr.org/), i.e. after a sentence ends, however long that sentence turns out to be. This keeps diffs sentence-scoped instead of reflowing whole paragraphs, and rendering is unaffected since Markdown joins consecutive lines into one paragraph.
- Kotlin/JS renders a whole `Double` without its fractional part (`2.0.toString() == "2"`, not `"2.0"`), so a common test asserting a literal `toString()` of a class with a `Double` property passes on JVM/Native and fails on JS. Assert the property values instead, or pick a type that renders identically everywhere.
- A `data` class hashes and renders an **array** member differently per platform: the JVM/Native `dataClassArrayMemberHashCode` intrinsic hashes by content, while the JS backend maps it to `jsHashCode` (identity) and renders `[...]`. Common tests must therefore assert *parity with an equivalent `data` class*, never a literal hash or `toString`.

- All three consumers of `dataApiViolation()` — the checker, the generator *and* `DataApiStatusTransformer` — must agree. The status transformer is easy to forget: matching only the annotation there leaves a checker-rejected class with `private` constructors and no builder to reach them, so every call site and subclass reports an inaccessible constructor on top of the one diagnostic the user is meant to read.
- `@DataApi` on a `data` or `value` class must be rejected outright. The two generators produce the same members, and the collision is not a diagnostic but a Fir2Ir crash (`NoSuchElementException` in `IrBasedDataClassMembersGenerator.generateCopyFunction`), because the plugin's `copy(block: Builder.() -> Unit)` gets picked up as the data class's own `copy` and no constructor parameter matches it.
- A `private` primary-constructor property must have a default value. The builder mirrors each property at its declared visibility, so a private one is assignable by nothing at all — and since the constructor is private too, a private property without a default leaves the class with no construction path whatsoever.
- Generated declarations must carry the annotated class's **visibility**; `create*Function` defaults to public. An `internal` class silently getting a public factory is a public entry point to a type kept out of the module's API, and an unexpected `apiCheck` failure. The one exception is the *top-level* factory of a `private` class: it lands in a generated file facade of its own, where `private` — a per-*file* visibility in Kotlin — would put it out of reach of the very file declaring the class, so it is clamped to `internal`.
- A user-declared `equals`/`hashCode`/`toString` is recognised by the **`override` modifier**, not by the parameter type. Overriding is the only way to declare the members the plugin would clash with, while an unrelated overload (`fun equals(other: Money)`) cannot carry it; and the modifier is readable without touching a type, which the phase `getCallableNamesForClass` can run at forbids. Matching `Any?` by the name in the type reference instead both misses a type alias for `Any?` (platform declaration clash) and falsely matches an unrelated user type called `Any` (class silently keeps identity equality).
- Do **not** try to detect a user-declared factory clashing with the generated one. Matching by name is the only test available at the phase the checker and generator share, and it falsely rejects a perfectly legitimate convenience overload of a different signature — worse than the bare `Conflicting overloads:` the real clash already produces.
- Diagnostics are tested by compiling source snippets in-process with [kctfork](https://github.com/ZacSweers/kotlin-compile-testing) (`dev.zacsweers.kctfork:core`, in the **compiler-plugin** module's own `src/test/kotlin`, not in `xemantic-kotlin-data-api-test`, which can only exercise code that compiles). Pick the kctfork version by the Kotlin it is built against — 0.13.0 targets 2.4 — and note four things: its `KotlinCompilation` API needs `@OptIn(ExperimentalCompilerApi::class)` or every use is a hard error under `progressiveMode`; `inheritClassPath = true` is what puts `@DataApi` on the snippet's classpath; `result.diagnosticMessages` carries the bare message text with no location prefix, so assertions can compare the whole string; and each snippet is a full compiler run (~1.5s), so a case earns its keep or does not get written.
- Assert the **whole** error list, never `contains`. Reporting exactly one diagnostic is the property most worth testing: `dataApiViolation()` has three consumers that must agree, and when any two disagree the violation is still reported — just buried under the unresolved references and inaccessible constructors that follow it.

## Test conventions

- Tests use [com.xemantic.kotlin.test](https://github.com/xemantic/xemantic-kotlin-test) (`should`/`have`/`assert`), name functions `should …`, and structure bodies with `// given` / `// when` / `// then` comments (omit a section when empty; for `assertFailsWith`, put `// when` inside the lambda and `// then` on the assertion).

## Anti-patterns to avoid

- Do not add content to this file that is already discoverable by reading the source or build scripts — that inflates context without adding signal, reducing AI agent task success rates (see [arxiv 2602.11988](https://arxiv.org/abs/2602.11988)).
